Concept 08

Keel — an agentic control plane for server fleets

Runs your fleet. Never without asking. The design question underneath: how do you give an agent root on production and keep a human accountable?

The original pitch

An “Agentic OS” that runs as the base for all the servers powering the world. Imagine stable Linux server operating systems, but agentic — so the higher-ups no longer need to hire and pay people to run and maintain them (updates, fixes, the usual Linux lifecycle). Everything done in plain-English speech.

Viability assessment

The problem is real and big. The framing has a fault line: it bundles two bets — that agents should run infrastructure (correct, crowded), and that this therefore means shipping a new OS (the part that breaks).

What already exists, September 2026

  • SUSE SLES 16 — first enterprise Linux with a built-in agentic AI framework. Agents query system state, evaluate options within policy constraints, perform bounded actions. GA November 2025, MCP baked in, instant rollback of upgrades/patches/config edits, 16-year lifecycle.
  • Red Hat Lightspeed — shell-level assistant in RHEL 10 for troubleshooting and compliance.
  • Canonical Ubuntu 26.04 LTS (April 2026) — positioned for the “agentic era”, layered isolation so agents run with controllable blast radius.
  • The AI SRE layer is fully capitalised: Resolve.ai (unicorn), Traversal (Sequoia, Kleiner Perkins), Datadog / Azure / incident.io all ship agents. NeuBird reports ~230,000 alerts autonomously resolved in a year.
  • Literal versions of the idea exist as hobby projects — CX Linux, AgntOS (NixOS), LinuxOS-AI. None have traction.

Why the OS framing is the weak leg

  1. Nobody swaps their OS. Hardware, drivers, compliance audits and support contracts are certified against RHEL/Ubuntu/SLES. A startup distro doesn’t get booted in production. Shipping an OS is a distribution problem first; the engineering is the easy half.
  2. The pain isn’t where the pitch aims. Updates and fixes were automated 15 years ago. What still burns money: incident diagnosis, config drift, capacity, security posture, migrations. Patching is the cheap part.
  3. “No humans needed” is the wrong promise. Every serious vendor sells human-in-the-loop, because a wrong rm at 3am is unbounded liability. Telling a CTO you’ll fire their ops team makes you the defendant in the next outage.
  4. The English interface is a feature, not a moat. Everyone shipped it. A weekend to demo, zero time to copy.

What is actually worth building

The instinct about the OS layer is half right: autonomy is only safe when the substrate guarantees rollback — immutable base, A/B slots, declarative config, transactional updates, append-only audit ledger. That is an OS-level property. The move is to build it as a control plane on top of existing distros and let SUSE and Canonical keep the distro business.

  • Wedge on one boring workflow with hard ROI — CVE remediation with provable rollback, or EOL migrations. Deterministic, verifiable, currently outsourced to consultancies for seven figures.
  • Sell to the underserved middle — MSPs and hosting providers. An MSP bills per node per month; if one tech manages 5× the fleet, pricing writes itself.
  • Compete on trust architecture, not intelligence — policy-as-code gates, signed action ledgers, simulated dry runs, one-command rollback. The model is a commodity; the safety envelope is the product.

The argument for narrowing: four different screens, four definitions of “done”. Design for all four and you get a chat box and a dashboard — what every hobby project already produced. Craft signal comes from specificity: which action needed a gate, why the rollback affordance sits there, what happened at 2am when the agent was wrong.

The open input the decision actually hinges on: which segment can realistically produce three or four real conversations in the next two weeks. Research access beats theoretical market size.

The demo

Standalone HTML, scroll-based narrative, seven sections. Fonts: Instrument Sans and IBM Plex Mono. Tokens: ink #0C1A29, surface #13263A, bone #E9EEF3, haze #93A7BC, amber #FFB020, mint #6FD3A8, alert #FF6B5B.

  1. Hero — “Runs your fleet. Never without asking.” A console types upgrade the fleet to the 6.12 kernel before sunday and ends in a “Held for approval” state: 240 nodes, 3 batches, 41 min, reboot required.
  2. Problem — “The work is boring. The risk is not.” An animated 240-node fleet grid where nodes drift amber and go unreachable red on scroll.
  3. Architecture — “Three things sit between a sentence and root.” Intent (sentence → named plan with blast radius) / Policy (runs unattended, waits for a person, never runs — “the agent proposes, policy consents”) / Transaction (every change lands on a snapshot or boot slot; a failed health check auto-reverts).
  4. Walkthrough — the interactive centrepiece. A kernel upgrade across 240 nodes at 01:12 IST. Intent → Plan → Dry run → Gate → Apply → Verify → Revert. The user must click Approve batch 1, or Hold until morning, which is a first-class ending: “Nothing moved”. On approve: 24 nodes upgrade, 22 pass health, 2 fail (nic driver not loaded), auto-revert to slot A in 19s, batches 2–3 halted. Verdict: “24 nodes changed. 2 reverted in 19 seconds. 216 never touched. Nobody was woken up.”
  5. Ledger — append-only, signed. Six entries from intent-opened to auto-revert, each with a hash and the policy rule that permitted it (kernel.requires_human).
  6. Stack — “It is not a new operating system.” Three bands: your workloads / Keel / Debian·RHEL·Ubuntu·SUSE, with support contracts and certifications still valid.
  7. Close — three unanswered questions, and a footer stating that no product exists behind the page.

Open design questions

  1. Who holds the pager when the agent is wrong? Auto-revert covers failures a health check can see; it does nothing for the quiet ones where every check passes and something is subtly broken for nine hours. Accountability has to be designed, not designed away.
  2. What does policy look like to someone who has never written policy? If authoring rules feels like firewall config in 2009, people approve everything by default and the gate becomes decoration.
  3. How does trust get earned? Probably one action class at a time — log rotation before kernels, read-only before write. The product may be less about capability and more about a ladder someone climbs over months.

Where it stands

  • All copy in the demo is placeholder-grade and expected to be redlined, especially the hero.
  • The segment decision is parked pending research access.
  • Nothing has been built beyond the demo. No case-study write-up exists yet.
  • Suggested next: pick the segment, get three or four real conversations, then design the policy-authoring surface — the weakest part of the current story — and the approval console.
